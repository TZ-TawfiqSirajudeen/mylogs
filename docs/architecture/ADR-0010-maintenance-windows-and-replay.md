# ADR-0010: Recurring maintenance windows and a bounded replay policy for missed evaluations

Status: accepted · Date: 2026-11-04 · Builds on ADR-0006 (alerting, decisions 6, 8, 9, 13 and the "one evaluation per interval, no catch-up" limitation)
User guide: [alerting.md](../alerting.md) · Operations: [runbooks/alerting.md](../runbooks/alerting.md)

## Context
ADR-0006 left two gaps that operators hit quickly:
1. **Silences are one-off.** Planned work that happens every Sunday 02:00 needs a person to create a silence every week, and a "daily 22:00 for 2 h" window cannot be
   expressed at all. Time zones and daylight saving make hand-computed UTC silences wrong twice a year.
2. **A stopped worker loses evaluations.** If the worker is down (or a lease expires) the rule simply continues at the current time: a breach that began and ended during
   the outage never produced a state transition, and a `for` duration that elapsed during the outage is not credited.

## Decisions

| # | Decision | Why / consequences |
|---|---|---|
| 1 | **Maintenance windows are a fourth `kind` (`maintenance`) in `alert_config`**, next to rule, channel and silence. No new collection and **no migration**: the existing indexes already serve them (`acfg_name_uq` makes the name unique per project and kind, `acfg_scope_kind` serves the list, `acfg_silence_ttl` removes finished one-off windows because only they carry `expireAt`). Migration number 31 was reserved for this work and is **not used**; the declared collection count (26 + `schema_migrations`) is unchanged. | A new schema version would have bought nothing. New rule fields are optional on stored documents and defaulted when read, so existing rules behave exactly as before. |
| 2 | **Schedule model.** `schedule` is either `{ type: "once", startsAt, endsAt }` (at most 30 days) or `{ type: "weekly", timezone, weekdays[mon..sun], startTime "HH:MM", durationMinutes 1..1440 }`. The timezone is an **IANA name** (`Europe/Berlin`, `UTC`); numeric offsets such as `+05:00` are refused because they cannot follow daylight saving. | Weekly windows are what operators ask for; anything more general (cron, monthly) is not built. |
| 3 | **Pure, clock-injected schedule functions** (`maintenance.ts`: `isActiveAt`, `activeOccurrenceAt`, `nextOccurrenceAfter`, `validateSchedule`), built only on `Intl.DateTimeFormat` (no date library, no `Date.now()`). A weekly occurrence **starts at local wall-clock time on the listed weekday**; its **duration is elapsed real time**, so a 02:00 + 3 h window is 3 real hours on the night the clocks change (it ends at 05:00 or 06:00 wall-clock, not "05:00 local" regardless). A window whose duration crosses midnight belongs to the weekday it **starts** on. | Anchoring the start to local time is what people mean by "every Sunday 02:00"; measuring the end in elapsed time keeps the function total and unambiguous. |
| 4 | **DST rules, stated once.** A local start time that does not exist (spring forward, e.g. 02:30 on a night 02:00 jumps to 03:00) is **shifted forward by the length of the gap** (02:30 becomes 03:30 wall-clock, a start at 02:00 becomes 03:00; the same convention as `Temporal` "compatible"). A local start time that exists twice (fall back) uses the **first** occurrence. | Deterministic and documented; both cases have tests. |
| 5 | **Behaviour while a window is active: evaluation continues, incidents are opened and recorded as usual, notifications are suppressed.** Each suppressed notification is recorded as a delivery with status `suppressed` and `maintenanceId` set, and as a `notification_suppressed` timeline event (`data.reason = "maintenance"`). No new incident flag or event type. A silence that also matches takes precedence in the record (it is the more specific, explicit act). | Same contract as silences (ADR-0006 #13): nothing disappears silently and maintenance cannot hide an incident in the UI. The alternative (pausing evaluation) would leave stale state across the window and lose the "it is still broken after maintenance" signal. |
| 6 | **Matching** is the silence vocabulary: rule ids, severities, environments (AND across kinds, empty = whole project). A window is judged **at the time the notification is created** and, for replayed transitions, **also at the time the transition happened** (a breach that began inside a window is still "during maintenance" when a late worker processes it). A disabled window never matches. | |
| 7 | **Limits and RBAC.** At most 20 windows per project (**counted** inside the creating transaction rather than kept in a counter, because finished one-off windows are removed by the TTL index and a counter would never see that; two concurrent creates at the limit can overshoot by one), name unique per project, reason up to 500 characters. Reading needs `alert:read`; create, edit, delete need `alert:manage` and, like channels and silences, **unrestricted environment access** (windows are project-wide). Every change is an audit event (`alert.maintenance.created/updated/deleted`) written in the same transaction; edits use optimistic `version`. Projects without access are 404. | Reuses existing policy actions: no change to `policy.ts`. |
| 8 | **Replay policy per rule:** `missedPolicy: "skip" | "replay"` (default **skip**, today's behaviour), `maxReplayEvaluations` 1..20 (default **5**) and `staleNotificationSeconds` 0..86400 (default **900**). These are *not* "semantic" fields: changing them does not reset state or close incidents. | Opt-in, so no existing rule changes behaviour on upgrade. |
| 9 | **What is a missed evaluation.** A claimed rule has a scheduled time `s0 = nextEvalAt`. With interval `I` and the claim time `now`, `n = floor((now - s0) / I) + 1` boundaries are due. The newest is satisfied by the evaluation that is happening now; the **`n - 1` earlier boundaries were missed** (`s0, s0+I, …`). Under normal operation `n = 1` and nothing is missed; a worker that is merely a few seconds late never counts. | Pure function (`replay.ts: planCatchUp`), unit-tested. |
| 10 | **Skip** (default): evaluate once at `now`, as before. The missed boundaries are only **counted** (`missed.skipped`). **Replay:** the most recent `min(N, n - 1)` missed boundaries are evaluated **in chronological order, each with the query window ending at that boundary** (event time: `evaluateQuery(rule, deps, boundary)`), through the unchanged state machine with the boundary as its clock, so `pending → firing → resolved` and the `for` and `resolveAfter` timers reflect what the data says happened. Older missed boundaries beyond N are counted as skipped. Then the normal evaluation at `now` runs. Incident `openedAt`/`resolvedAt`, timeline `at`, the group's `since`/`lastEvalAt` carry the boundary (**event time**); timeline events of replayed transitions carry `data.replayed = true`, `data.evaluatedAt` (the boundary) and `data.processedAt`. | Bounded work: at most 20 extra evaluations per claim, each with its own time budget, plus an overall replay budget. A failed replayed evaluation changes nothing (ADR-0006 #6) and counts as skipped. |
| 11 | **Idempotency and two workers.** Replay progress is persisted **after every boundary** in the same guarded update the engine already uses (`_id`, `version`, `lease.owner`), which also advances `nextEvalAt` to the boundary after it and **renews the lease**. A crash resumes at the next boundary; a worker that lost its lease (or whose rule was edited) gets a zero-match update and **stops without writing**. Side effects stay idempotent: `incidents.open` relies on the unique partial index `inc_active_uq` (ADR-0006 #7, unchanged), `autoResolve` returns nothing when no incident is live. Counters use `$inc` in the guarded update, so a retried step is not counted twice. | Residual edge, stated honestly: a worker that stalls *between* an incident write and its guarded state write can be overtaken by the new lease holder; the effects are idempotent, but a transition may be applied once more from the other worker's point of view. |
| 12 | **No notification storm after a long outage.** For a replayed transition older than `staleNotificationSeconds` at processing time, nothing is sent: the delivery row is recorded with status **`stale`** (new, next to `suppressed` and `rate_limited`) and the timeline gets a `notification_suppressed` event with `data.reason = "stale"`. Younger replayed transitions are sent normally (subject to silences, maintenance windows and the channel rate limit, which still apply). **Catch-up notice:** a still-firing incident whose opening was recorded as stale gets **one** notice describing the current state (`incident.opened`, `data.catchUp = true`) when the replay ends, and an incident that had been announced and was closed during the replay gets one `incident.resolved` notice; so the worst case is one notice per incident, equal to what normal operation would have sent, never one per replayed transition. | Without the catch-up notice the replay policy would be *quieter* than skip for a real ongoing outage. A crash between replay steps loses the in-memory catch-up decision (the incident and its stale records remain visible): documented, not hidden. |
| 13 | **Status API/UI.** The rule DTO gains `missedPolicy`, `maxReplayEvaluations`, `staleNotificationSeconds` and `missedEvaluations { total, replayed, skipped, lastAt }` (cumulative since creation; `lastEvaluatedAt` keeps meaning "the last evaluation that ran": the real time of the current evaluation). The Prometheus endpoint gains `nexus_alert_evaluations_missed_total` and `nexus_alert_evaluations_replayed_total`. | Operators can see that a rule had a gap and what was done about it. |

## Data model (all inside existing collections)
- `alert_config` `kind: "maintenance"`: `{ _id, orgId, projectId, name, nameLower, comment, enabled, schedule, matchers, version, createdBy, createdAt, updatedAt, expireAt? }` (`expireAt` only for `once`, end + 1 day).
- `alert_config` `kind: "rule"`: optional `missedPolicy`, `maxReplayEvaluations`, `staleNotificationSeconds`, `missed { total, replayed, skipped, lastAt }`.
- `alert_deliveries`: optional `maintenanceId`; `status` gains `stale` (the 30-day TTL applies as before).

## API
`GET/POST /api/v1/projects/:projectId/alert-maintenance-windows`, `GET/PATCH/DELETE …/:windowId`. The DTO adds computed `state` (`active`, `scheduled`, `expired`, `disabled`), `activeNow` and `nextOccurrence` / `currentOccurrence` (UTC instants), evaluated by the server clock.

## Not built (honest list)
Cron expressions, monthly or "last Friday" schedules, windows longer than 24 h for weekly schedules, exclusion dates (public holidays), per-window notification of a start/end, automatic notice when a window ends while an incident that opened inside it is still firing (it stays visible in the UI; nobody was paged), replay of more than 20 boundaries, replay that preserves the exact pre-outage state for boundaries older than the replayed ones, and crash-proof catch-up notices.

## Testing
Pure schedule functions (spring forward and fall back in `America/New_York`, `Europe/Berlin`, a half-hour-offset zone, midnight crossing, invalid input), `planCatchUp`, engine tests with the fake clock simulating an outage (skip vs replay, stale suppression, catch-up notice, idempotent re-run, two engines racing), real-store tests against the real metric store with a replayed outage, API tests (CRUD, RBAC, tenant isolation, limits, audit) and `tests/e2e/specs/21-maintenance-windows.spec.ts`.
