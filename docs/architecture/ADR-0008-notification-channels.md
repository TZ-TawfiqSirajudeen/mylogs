# ADR-0008: Notification channels beyond the generic webhook (Slack, e-mail)

Status: accepted (written before the code, then amended with the final port policy) · Date: 2026-11-04 · Builds on ADR-0006 (decisions 10-14: channel secrets, SSRF, delivery queue, silences, audit), ADR-0002 (secrets, SSRF guard)
User guide: [alerting.md](../alerting.md) · Operations: [runbooks/alerting.md](../runbooks/alerting.md)

## Context
ADR-0006 shipped webhook channels only. Most teams want the incident in Slack and in an inbox. Both are outbound network calls to an address a project
admin typed in, so the ADR-0006 rules (secret handling, SSRF, queue, retries, silences, audit) must apply unchanged; the new work is *formatting* and *transport*.

## Decisions

| # | Decision | Why / consequences |
|---|---|---|
| 1 | **One channel collection, three `type`s:** `webhook` (unchanged), `slack`, `email`. Same `alert_config` documents (`kind: channel`), same quota (10 per project), same name uniqueness, same per-channel rate limit, same test-send (5/min), same delivery rows. **No migration.** | Queue, retry, silence, rate-limit, audit and the delivery log are type-agnostic: `DeliveryProcessor.attempt` picks a *transport* by `channel.type` and everything after the result (status, backoff, timeline, metrics) is shared code. |
| 2 | **Slack = incoming webhook.** The full webhook URL (its path is the credential) is envelope-encrypted in `SecretStore` (`alert-channel:<id>` / `url`); the document and every API response keep only `https://host/…`. The message is Block Kit (header, severity/status/rule/condition/value/group fields, context line, a "View incident" button when `WEB_ORIGIN` is set) plus a plain-text `text` fallback. No signing secret (Slack has no receiver-side verification for incoming webhooks). | A Slack webhook URL *is* a bearer secret, so it is treated exactly like a webhook signing secret. Other Slack-compatible receivers (Mattermost, self-hosted) work, because the guard, not a hostname allow-list, is the safety control. |
| 3 | **Slack text is escaped, not trusted.** Every dynamic value is mrkdwn-escaped (`&`, `<`, `>` become entities) so a metric label or service name cannot produce `<!channel>`, `<@U123>` or a phishing `<https://evil|text>` link; values are truncated to Slack's block limits; the request stays under the 16 KiB cap. | Labels come from telemetry, i.e. from whoever can send data. |
| 4 | **E-mail = SMTP submission with a small in-repo client (`smtp.ts`), not nodemailer.** Capabilities: implicit TLS (465) or STARTTLS (587, required: a server that does not offer it is a failure, never a silent downgrade), AUTH PLAIN/LOGIN, one message to up to 20 recipients. Plain `none` security is accepted only when the platform policy allows insecure http (development). Certificates are always verified. | `nodemailer` is not in the lockfile or the offline pnpm store, and a library connects by host name, so DNS-rebinding protection would need patching its transport anyway. The client is about 200 lines, has no parser for untrusted input beyond SMTP reply lines (capped), and connects only to validated, pinned addresses. The trade-off (feature poverty: no DKIM, no OAuth2, no attachments, no pipelining) is listed below. |
| 5 | **SSRF for SMTP reuses `resolveSafeTarget`** with the same policy as webhooks: the host is resolved and every address checked at save time and again on every send; the socket is pinned to the validated addresses (`pinnedLookup`); private, loopback, link-local and metadata addresses are refused unless the operator approved them (`NETWORK_ALLOW_PRIVATE_CIDRS`). The generic guard blocks mail ports; for SMTP only **587, 465 and 2525** are accepted (`allowPorts`), **every other port, port 25 included, stays blocked** (25 is the relay port and the usual SSRF/spam target; an operator moves the relay to 587/465). The development switch (the same `NETWORK_ALLOW_INSECURE_HTTP` flag that permits plain http webhooks) also permits other ports and `security: none`, so tests can reach an in-process server. | A project admin must not be able to turn the alerting worker into a port scanner or open mail relay. |
| 6 | **E-mail secrets:** the SMTP user name and password are envelope-encrypted (`smtp-user`, `smtp-pass`), write-only (`hasSmtpCredentials` is the only thing returned), never in the document, audit metadata, logs, delivery errors or timeline. Delivery errors carry the SMTP *reply code* and a fixed sentence, never the server's text (a server could echo a command). Recipients and the from-address are not secrets and are stored in the channel document; the API returns **masked** recipients (`a***@example.com`) to readers. | Least exposure: a viewer can read channels but should not harvest team mailboxes. Admins re-enter the full list to change it. |
| 7 | **Address and header safety.** Recipients and `from` must match a strict ASCII addr-spec (letters, digits, `. _ % + -` in the local part, a dotted host name), at most 254 characters, lower-cased, de-duplicated; **at most 20 recipients**. The check runs in the contract, in the service, and again in the SMTP client immediately before the command is written, so a bad value in an old document still cannot inject `\r\n` into SMTP commands or headers. The subject is stripped of control characters and RFC 2047-encoded; the display name is fixed. | No user-controlled string reaches a header or command without passing a character whitelist. |
| 8 | **Bodies:** `multipart/alternative` with a plain-text part first and an HTML part second, both UTF-8 base64. Every dynamic value in the HTML is entity-escaped; the incident link is included only when it is an `http(s)` URL and is escaped as an attribute. `Message-ID` is derived from the delivery id, `X-Nexus-Delivery` and `Auto-Submitted: auto-generated` are set. | Escaping is done once, in one function, with tests for the classic payloads. |
| 9 | **Retry classification for SMTP:** connection errors, time-outs and 4xx replies are retried with the ADR-0006 backoff; 5xx replies, authentication failures, a missing STARTTLS, TLS certificate errors and blocked targets fail at once. If some recipients are refused but at least one accepted the message, the delivery counts as delivered and the timeline says how many were refused (a retry would re-mail the accepted ones). Delivery stays **at-least-once**; the stable `Message-ID` lets a mailbox filter duplicates. | Same semantics as webhooks without inventing a second queue. |
| 10 | **Timeouts and caps:** 20 s overall per SMTP delivery (5 s to connect), reply lines capped at 1 KiB and replies at 8 KiB, message capped at 64 KiB, Slack/webhook caps as in ADR-0006 (5 s, 16 KiB, 2 KiB read). | A slow or hostile server cannot hold a worker lane. |
| 11 | **Contracts:** `ChannelCreate` is a discriminated union on `type`; `ChannelUpdate` stays a flat partial and the service rejects fields that do not belong to the channel's type. `ChannelDto` adds `smtp`, `from`, `recipientsMasked`, `hasSmtpCredentials` **for e-mail channels only** (absent otherwise, so webhook responses are byte-for-byte what they were); `hasSigningSecret` is true for webhooks only. Existing webhook requests and responses are unchanged. | Backwards compatible for existing clients and tests. |
| 12 | **Audit:** unchanged mechanism (`alert.channel.created/updated/deleted/tested`). Metadata carries type, name, the display target (`https://hooks.slack.com/…`, `smtp://host:587`) and updated field *names*; never the Slack URL, SMTP credentials or recipient addresses. | ADR-0006 #14. |

## Not built (honest list)
Teams, PagerDuty/Opsgenie, SMS · Slack OAuth apps / threads / interactive buttons (acknowledge from Slack) · DKIM, SPF alignment help, OAuth2 SMTP (Gmail/Microsoft 365 without an app password), attachments, SMTP pipelining, SMTPUTF8 (non-ASCII addresses) · per-recipient delivery state (one delivery row per channel and event, not per recipient) · mailing-list digests or batching · a bounce handler · exactly-once delivery · per-user notification preferences · a hostname allow-list for Slack URLs.

## Known limitations that matter
- **Verified only against in-process fakes.** The Slack path was tested against a local HTTP receiver and the SMTP client against a scripted in-process SMTP server (including STARTTLS with a self-signed certificate via a test-only trust hook). No real Slack workspace or real mail provider was used; provider quirks (for example servers that require `AUTH` before `STARTTLS` capability refresh, or ones that rate-limit by sender) are untested.
- **Port 25 and every port other than 587/465/2525 is refused** by design (decision 5); a relay that only listens on 25 needs a 587/465 listener in front of it.
- **E-mail may duplicate** after a crash between the server's `250` and the status write; the `Message-ID` is stable across retries.
- Mail from a shared provider needs the `from` address to be authorised by that provider (SPF/DKIM are the provider's concern, not Nexus's).

## Consequences found while building it
- `ChannelUpdate` is built with `.partial()`; zod applies `default()` inside a partial, so the old update schema silently reset `rateLimitPerMinute` to 20 on every unrelated PATCH (for example just toggling `enabled`). The update schema now has no defaults and a test pins it.
- `ChannelService` and `toChannelDto` moved from `config.ts` to `channels.ts` (config.ts had grown to rules, channels and silences, and three work streams edit alerting concurrently). `takeSlot`/`releaseSlot` are exported from `config.ts` for it.
- Contracts: the channel schemas moved to `packages/contracts/src/alert-channels.ts` (still exported from the package index).
