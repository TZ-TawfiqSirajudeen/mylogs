# ADR-0011: Deployments (change markers)

Status: accepted · Date: 2026-11-04 · Builds on ADR-0001 (tenancy, RBAC, audit), ADR-0003 (ingestion tokens), ADR-0005 (metric/trace query APIs), ADR-0006 (incidents)
Reference: [deployments.md](../deployments.md)

## Context
`/deployments` was a placeholder. A deployment is the single most useful fact to have next to a chart or an incident ("what changed?"), and it is cheap to
record: CI knows the service, the version and the outcome. This slice records deployments, lets CI write them with an ingestion token, shows them as
markers on the metric charts and as context in an incident. It is deliberately **not** a deployment tool: Nexus never triggers, approves or rolls back anything.

## Decisions

| # | Decision | Why / consequences |
|---|---|---|
| 1 | **No new workspace package: a clearly separated module `packages/ingest/src/deployments/`** (own barrel `index.ts`, no imports from the rest of `@nexus/ingest` except the token type), DTOs in `@nexus/contracts` (`deployments.ts`), the stored document in `@nexus/database` (`deployment-models.ts`). | The write path is a token-authenticated *sender* API, like telemetry: it reuses `IngestTokenService`, `RateLimiter` and the token scopes that already live in `@nexus/ingest`. A new package would also need `pnpm install` (lock file), a `Dockerfile` COPY line and a worker/API bundle entry for no code that is shared with anything but ingest. The module is self-contained, so extracting it into `@nexus/deployments` later is a move of one folder plus a `package.json`. |
| 2 | **One new collection `deployments`, migration version 32 only.** Nexus declares 27 collections + `schema_migrations` = **28 of the Atlas free tier's 500** (+1 over the 27 of ADR-0006/0007; collections added by other work streams are not counted here). | Deployments are small, append-mostly documents; a collection per concern is the existing pattern. |
| 3 | **Fields:** `orgId, projectId, environmentId` (always from the credential), `service` (1–128), `version` (1–128), `commitSha` (optional, 7–64 hex, lower-cased), `status` (`started`, `succeeded`, `failed`, `rolled_back`), `startedAt`, `finishedAt`, `notes` (≤ 1,000 characters), `linkUrl` (https only, ≤ 2,000), `triggeredBy` (optional free-text label of the CI actor, ≤ 100), `idempotencyKey` (optional, ≤ 128), and a **server-derived** `actor` (`token` + token name, or `user` + display name). `expireAt` = `startedAt` + 365 days (TTL). | The actor is derived from the credential, so a sender cannot impersonate a user; `triggeredBy` is explicitly a label, shown as such. |
| 4 | **Text is data, never markup.** All text fields are stored as text, control characters are removed (newline and tab are kept in notes only), notes are passed through the platform's credential scrubber (`scrubText`) before they are stored, and the UI renders every field as a React text node (no `dangerouslySetInnerHTML`, no Markdown, no auto-linking). The only clickable value is `linkUrl`, and only if it parses as `https:` with a host, no user-info (a fragment is allowed); it is rendered with `rel="noopener noreferrer nofollow"`. `javascript:`, `data:`, `http:`, `file:` and protocol-relative values are refused at the API (400). | Stored XSS is prevented at two layers (validation and rendering). The URL is never fetched by the server, so SSRF does not apply; the scheme check exists for the browser. |
| 5 | **Write API `POST /api/v1/deployments`** accepts either an **ingestion token** with the new `deployments` scope (`Authorization: Bearer nxi_…` or `X-Nexus-Token`) or a **user session** (cookie + CSRF + origin check, role engineer or project admin, and access to the environment). With a token, `orgId`, `projectId` and `environmentId` come **only** from the token; a payload that names them is refused (400 `scope_in_payload`) instead of being ignored. With a session the body must name `projectId` and `environmentId`, and both are authorized against the caller's grant (environment-restricted users cannot write outside their scope; an environment they cannot see is a 404). | CI has no cookie. A presented token never falls back to the cookie (and a bad token is 401, not "try the session"). The route does not use `app.authenticate` (which is cookie-only), so it is added to the route-inventory allow-list in `oidc.test.ts` **deliberately**, with its own 401/403/forged-credential tests. |
| 6 | **Token scope `deployments` is added minimally:** the scope list is `logs`, `traces`, `metrics`, `deployments`. It is **opt-in**: the default for new tokens stays the three telemetry signals, existing tokens are not widened, the ingestion service keeps checking `scopes.includes(signal)` (a deployments-only token cannot send telemetry, a telemetry token cannot write deployments), and a token never grants any read access. Token creation stays `connection:manage` (project admin). | Least privilege: a CI token that can only write deployment records for one environment. Leaking one lets an attacker add misleading change markers to that environment (see "Security properties"), not read data or send telemetry. |
| 7 | **Idempotency on `idempotencyKey`**, unique per `(orgId, environmentId, idempotencyKey)` (partial unique index, only when a key is present; no key = no de-duplication). Same key and same identity (`service`, `version`, and `commitSha` when sent) = the same deployment: an identical replay answers 200 `unchanged`; a **legal status progress** answers 200 `updated`; a different identity answers **409 `idempotency_conflict`**. A first write answers 201 `created`. Allowed progress: `started` → `succeeded` / `failed` / `rolled_back`; `succeeded` / `failed` → `rolled_back`; nothing leaves `rolled_back`; going backwards (e.g. `succeeded` → `started`) is a 409 `invalid_transition`. `startedAt` of a replay is ignored (a retry that recomputes "now" must not conflict). Concurrent first writes race on the unique index; the loser re-reads and takes the replay path. Updates are conditional on the status the decision was made on (no lost update). | CI steps retry and report twice (`started`, then `succeeded`) with the same key. |
| 8 | **Abuse limits:** per credential 30 writes per minute (token hash, or session), plus the platform's per-IP limit; failed token authentication is throttled per client address (30/min, same as ingestion) and answered identically for unknown, malformed and revoked tokens; body ≤ 16 KiB; **at most 2,000 deployments per environment per rolling 24 h** (429 `environment_limit`, counted with a bounded index scan); `startedAt` must be within the last 90 days and at most 5 minutes in the future; `finishedAt` must not precede `startedAt`. | Bounded growth and a cheap defence against a leaked token filling storage. |
| 9 | **Read API (session only, RBAC):** `GET /api/v1/projects/:projectId/deployments` (filters `environmentId`, `service`, `status`, `from`, `to`; keyset pagination, newest first), `GET …/deployments/:id`, `GET …/deployments/markers` (bounded, lightweight: at most 200, no notes) and `GET …/incidents/:incidentId/deployments` (correlation). Read needs `telemetry:read` (**viewer and up**; the same rule as every other telemetry read), the environment set is the caller's grant (`access.environmentIds`), and an item in an environment the caller cannot read is a 404, never a 403. Ingestion tokens do **not** authenticate these routes. | Reuses `makeAuthorize`; nothing in a request can widen the scope. |
| 10 | **Audit:** every create and status change is an audit event (`deployment.recorded`, `deployment.updated`) written in the same transaction as the write; the actor is the user, or (for a token) a `system` event carrying the token id and name (`senderId`, `senderName`: the audit redactor masks keys that contain "token"). Metadata has field names and the service/version/status only (never notes or the link). | Who or what recorded a change marker is answerable. |
| 11 | **Change markers on charts** are drawn by `TimelineChart` from an optional `markers` prop: a vertical line plus a handle per deployment, each an SVG element with `role="button"`, `tabindex="0"`, an `aria-label` and a native `<title>` with version, status and time; focus or hover shows the same text in a visible tooltip, Enter opens the deployment, Escape hides the tooltip. Colour is never the only signal (status glyphs ✓ ✕ ↺ ▶ and a text list of the markers under every chart). Markers are fetched separately from the data: if that call fails the chart is unchanged and says markers are unavailable. They are drawn on the Metrics explorer and on the service dashboard (per environment). | A marker is a fact ("this happened at 12:03"); the chart text says nothing about cause. |
| 12 | **Incident timeline:** `GET …/incidents/:incidentId/deployments` returns deployments **in the incident's environment**, of a service the incident is **about** (the rule's `service` for a metric rule, `services` for a log rule, and the group's `service` label), whose start is not after the incident opened and whose end (`finishedAt`, else start) is at most **30 minutes** before it opened. The UI renders each as a timeline entry worded *"deployed shortly before; correlation, not proof of cause"*. Read-only: nothing is created, nothing is linked back, the incident is not modified. A rule that names no service gets no correlation, and the page says so. | Honest, small and explainable. The pure matching function (`deploymentPrecedesIncident`) is unit-tested at the boundaries. The incident detail page gets one isolated component; the API route is in the deployments module, not in alerting. |

## Indexes (migration 32, asserted by tests)
- `dep_scope_started` `(orgId, projectId, environmentId, startedAt desc, _id desc)`: the list, the marker window and the 24 h counter. A multi-environment list is an `$in` on the first three fields followed by the sort key, which MongoDB serves with a merge sort (no in-memory sort; asserted by an explain test).
- `dep_scope_service_started` `(orgId, projectId, environmentId, service, startedAt desc, _id desc)`: service filter and incident correlation.
- `dep_idem_uq` unique `(orgId, environmentId, idempotencyKey)` partial `{ idempotencyKey: { $type: 'string' } }`.
- `dep_ttl` `expireAt` TTL (`expireAfterSeconds: 0`).
Rollback drops exactly these four indexes (the collection is left in place, like the other migrations).

## Security properties (each one has a test)
- No token, malformed, unknown or revoked token: 401, identical bodies; a telemetry-only token: 403 (`forbidden_scope`); a `deployments` token cannot read (401 on the read routes) and cannot send logs, traces or metrics (403 from the ingestion service).
- The environment comes from the token; a payload that names a project/environment is refused; a session user cannot write to an environment outside their grant or another tenant (404).
- Viewers cannot write (403); viewers can read; environment-restricted users see only their environments, on every read route including markers and incident correlation.
- Another tenant's deployment ids, incidents and idempotency keys are invisible and cannot collide (the unique index includes `orgId`).
- `<script>`, `<img onerror>` and other markup in service, version, notes and trigger label are stored inert and rendered as text (API test: returned verbatim as JSON strings; browser test: not executed).
- `javascript:`, `data:`, `http:`, `ftp:` and `//host` links are refused.
- **Residual risk:** a leaked `deployments` token can create *false* markers in one environment (rate limited, audited, expiring after 365 days, revocable). Markers carry their actor ("token: ci-prod") so a forged one is attributable to a token. Notes are scrubbed with the same best-effort redaction as logs; a secret the scrubber does not recognise would be stored and shown.

## Not built (honest list)
Triggering or rolling back deployments · webhooks from GitHub/GitLab/Argo/Flux (CI calls the API) · a UI form to record a deployment by hand (the API accepts sessions; the page has no form) · deleting or editing a deployment · automatic detection of deployments from telemetry (`service.version` changes) · deployment frequency / lead-time / change-failure-rate (DORA) views · markers on the Logs histogram and the trace views · deployment-aware alert rules · "this deployment may have caused" claims of any kind · per-token deployment retention (fixed 365 days) · exactly-once semantics beyond the idempotency key · rate limits shared across API replicas (they are per process, like the ingestion limits).
