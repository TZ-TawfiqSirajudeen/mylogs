# ADR-0009: Rule preview against history, and incident-to-trace/log links

Status: accepted · Date: 2026-11-04 · Builds on ADR-0006 (alerting), ADR-0005 (metric/trace/log navigation), ADR-0007 (rollups)
User guide: [alerting.md](../alerting.md) ("Previewing a rule", "Related telemetry on an incident")

## Context
ADR-0006 listed "a dry-run (preview) of a rule" as not built, and an incident page showed only the rule's numbers: finding the logs or traces behind an
incident meant re-typing the rule's filter into another page. Both are cheap to build *if* they reuse what exists, and both are easy to build wrongly:
a preview with its own threshold logic would drift from the real evaluation, and a "related traces" panel that implies causation would mislead people at
the worst moment. This ADR fixes the rules before the code.

## Decisions

### Rule preview
| # | Decision | Why / consequences |
|---|---|---|
| 1 | **`POST /api/v1/projects/:projectId/alert-rules/preview`**, authorized exactly like rule create: action `alert:manage` (project admin, org owner/admin implicitly), the rule's environment must be inside the caller's environment scope (otherwise `404`, as for create), projects without access are `404`. The body is the rule's *measuring* fields (query, condition, window, interval, for, resolve-after, no-data policy, environment) plus `rangeSeconds`; name, severity and channels are not accepted. It uses the same schemas and cross-field validation as create. | Previewing reveals what the stores contain for that environment, so it needs at least the right to create the rule. The body is `strict`: nothing in it can select another project, org or store. |
| 2 | **One code path.** For every evaluation time `t` of the range the preview calls the real `evaluateQuery(rule, deps, t)` (the clock is injected), then folds the per-group observations through the real state machine `step()` from `state.ts`, with `t` as `now`. `preview.ts` contains **no** comparison, aggregation or hysteresis logic. | A rule that previews as firing is judged by the same code as a rule that fires. Changes to the evaluator or the state machine change the preview with them. |
| 3 | **Bounds.** Range: default 6 h, minimum 5 min, maximum 24 h, always ending at the server's "now". Evaluation step = `max(rule interval, ceil(range / 199))`, so there are **at most 200 evaluation points**. At most 4 evaluations run at once; **at most 400 store queries** per preview (an `avg` rule needs two per point); a **15 s deadline** for the whole preview and the same per-rule budget as the engine for each point (10 s); at most **2 previews run at once per API process** (`429 busy` beyond that); at most **10 requests per minute per session**. Each store query keeps the store's own guards (series scanned, point documents scanned, `maxTimeMS`). Hitting the point, query or time limit returns what was evaluated so far with `partial: true` and a plain-language note; it is never an error. | A preview is a burst of read queries triggered by a button, so every dimension of it is capped. The cap on the number of queries makes the worst case independent of the data. |
| 4 | **Errors.** The first evaluation runs alone: a query the store refuses (unsupported aggregation for the metric type, `query_too_expensive`, a time-out) fails the whole preview with that message, instead of repeating the failure 200 times. A later point that fails is skipped, counted, and (like in the engine) **changes no state**; the response says how many were skipped. | Matches ADR-0006 #6: an evaluation error never resolves and never fires. |
| 5 | **Read-only by construction.** The preview service receives only the metric/log read interfaces (`EvalDeps`) and a clock, **no database handle, no incident service, no notifier, no lease and no audit sink.** It writes nothing: no incident, no notification or delivery, no rule state, no audit event (a read produces none, like every other query route). Tests assert the stores were only read and that the alerting collections and the audit log are unchanged after a preview. | A dry run that could open a real incident is not a dry run. |
| 6 | **Result.** Per group (up to 20, like the engine): the value series (`null` = no data, never drawn as zero), the state after every point (`ok`, `pending`, `firing`, `resolved`), the would-be periods (`pending` and `firing`, with start, end and whether they were still ongoing at the end of the range) and the number of incidents that *would have opened* (state-machine `fire` transitions). Totals: incidents that would have opened, groups that would have fired, evaluation points, points without data, skipped points. | The chart needs the series and the periods; the "would have opened N incidents" line needs the transitions, not the breach count. |
| 7 | **Plain-language notes, always computed on the server** so every client says the same thing: a no-data note (how many points had no data and what the chosen no-data policy did with them: kept the state / counted them as healthy / counted them as a problem), a coarser-step note (when the step is larger than the rule's interval, for-durations are approximated at that resolution), a start-state note (the replay starts from "ok": a problem already under way at the start of the range looks as if it started there), a groups-truncated note, a partial-result note. | Silent approximations would be the main way a preview misleads. |
| 8 | **The web form** has a Preview button next to Save, sends the draft exactly as Save would, and shows loading, empty (no data in the range), error and result states. The result is a small SVG chart per group (threshold line, shaded would-fire periods) with a text summary and a data table behind it for screen readers. | Accessibility: colour is never the only signal (periods are also listed as text). |

### Incident links
| # | Decision | Why / consequences |
|---|---|---|
| 9 | **No new API for links.** The incident page reads the incident's rule (`GET …/alert-rules/:ruleId`, `alert:read`) and builds links; the optional example traces use the existing authorized `POST …/metrics/query` and `POST …/traces/search`. If the rule was deleted, the panel says so and shows nothing. | Every read is authorized and environment-scoped by the route that already owns it; a viewer sees the same panel as an engineer (it only navigates). |
| 10 | **The window** of an incident is `[openedAt - windowSeconds, resolvedAt (or now) ]`, at least 5 minutes long and at most 24 h, in UTC ISO form. | The first value that breached was computed from the window before `openedAt`; the end is the resolution time or "now" for a live incident. |
| 11 | **Log-count rules** link to the Logs Explorer pre-filled with the rule's own filter (text, severity or errors-only, services, field filters), the rule's environment and the window. **Metric rules** link to the Metrics explorer with metric, service, label filters, group labels of the incident as extra filters, aggregation and the window (the explorer learns a `custom` range from `from`/`to`), and to the Traces explorer for the same service (errors only) in the window when a service is known. Up to **5 example traces** are listed: exemplars of the metric first, otherwise failed traces of the same service in the window. | Exactly what a responder would type by hand. |
| 12 | **Wording.** The panel states, next to every example list: *"A sample from the window, not proof of cause"*, and that traces are limited to what was sampled and received. Exemplars are labelled as exemplars (explicit references from the metric), failed traces as "failed traces of the same service in this window". | Same wording and policy as ADR-0005's metric/trace navigation; no causal claims. |
| 13 | **Links carry only ids, filters and times**: project id and environment id (the same `p`/`env` parameters every explorer link uses), the rule's declared filters, UTC times. Never tokens, secrets, webhook data or session information. The destination page authorizes whoever opens the link. | A link can be pasted into chat; the person opening it must still pass the server's checks. |

## Not built
Previewing a *saved* rule by id (the form previews its draft; for a saved rule the form is open with its values) · previews older than 24 h or arbitrary start/end · preview of silences, maintenance windows or notification delivery · reproducing the exact data a past live evaluation saw (see below) · a preview that continues from the rule's live state · links to dashboards, deployments or database-collector pages · automatic causal analysis.

## Known limitations
- **Hindsight.** The preview evaluates *today's* stored data at historical times. A live evaluation back then could not see records that arrived later (ADR-0006: log counts use event time), so a preview can show a breach the live rule would have missed, or the other way round for data that has expired. It is a plausibility check, not a replay.
- **Starts from "ok".** The state machine has no memory before the range; a breach already running at the start is shown as starting there (the note says so).
- **Cost** grows with the number of points, the window and the series scanned; the caps in #3 bound it. A preview over 24 h at a 15 s interval is evaluated at a ~7 min step (200 points).
- The stores answer each historical point with its own query. A prefetch-and-slice optimization was rejected for the first version because the store's whole-minute bucket edges would then have to be reproduced outside the evaluator, which is the duplication #2 forbids.
- Measured cost: see "Previewing a rule" in [alerting.md](../alerting.md).
