# ADR-0006: Alerting and incidents (first vertical slice)

Status: accepted · Date: 2026-11-02 · Builds on ADR-0001 (tenancy, RBAC, audit), ADR-0002 (secrets, SSRF guard, leases), ADR-0005 (metric/log query APIs)
User guide: [alerting.md](../alerting.md) · Operations: [runbooks/alerting.md](../runbooks/alerting.md)

## Context
Phases 1–5 can ingest, store and query telemetry but nothing *acts* on it. This slice adds the smallest alerting loop that is real end to end:
rules that read the existing stores, a state machine that decides when something is wrong, incidents people can act on, and webhook
notifications that cannot be abused to attack the network. It is deliberately a slice: what is not built is listed under "Not built".

## Decisions

| # | Decision | Why / consequences |
|---|---|---|
| 1 | **A new package, `@nexus/alerting`**, holds the state machine, evaluator, engine, incident service, notifier, delivery sender and the rule/channel/silence services. The API routes and the worker are thin shells around it. | API and worker must run the *same* code (incident open/close happens in the worker; acknowledge/resolve and test-send in the API). Only additive edits were needed in shared files (`models.ts`, `migrations.ts`, `app.ts`, `worker/main.ts`, nav). |
| 2 | **Three collections** (`alert_config`, `incidents`, `alert_deliveries`; Nexus goes from 22 to 25 declared collections; 26 on Atlas counting `schema_migrations`). Rules, channels and silences share `alert_config` and are told apart by `kind`; each kind is always part of the filter. Channel secrets reuse the existing `secrets` collection (namespace `alert-channel:<id>`). The incident timeline is **embedded** (bounded), not a collection. | Atlas free tier caps a cluster at 500 collections. A `kind` discriminator costs a little typing (typed views in `common.ts`) and nothing at query time: every query is scoped by `orgId, projectId, kind`. |
| 3 | **Rules are project-scoped and read exactly one environment.** The environment decides access: a project admin restricted to environments can only create/see rules and incidents of those environments (`canAccessEnvironment`); channels and silences are project-wide, so managing them requires unrestricted access. | Reuses the existing environment-scoped RBAC instead of inventing another dimension. Evaluation scope is taken from the rule document (org, project, environment), never from a request. |
| 4 | **RBAC** (existing roles, one new action each): `alert:read` = viewer, engineer, project admin; `incident:write` (ack, resolve, comment, already in the policy table) = engineer, project admin; `alert:manage` (rules, channels, silences) = project admin (org owners/admins implicitly). Projects without access are 404, never 403. | A viewer is read-only; "member can ack" is the project-role *engineer*. |
| 5 | **Query model:** a rule is either a *metric threshold* (aggregation over a sliding window of one metric, exact label filters, optional single `groupBy`) or a *log count* (the Logs Explorer filter vocabulary, validated by the same schema). Metric rules call `MetricStore.query`, log rules call `LogStore.histogram`; nothing reads the collections directly. | Stores stay swappable, query limits (series scanned, time-outs) apply to alerts too. **Percentiles are refused** at validation: a percentile of per-minute percentiles is wrong, and the store API does not expose mergeable buckets for an arbitrary sliding window. `avg` is computed as sum/count from two queries. |
| 6 | **State machine** `ok -> pending -> firing -> resolved` per (rule, group), a pure function with an injected clock (`state.ts`). `forSeconds` before firing; `resolveAfterSeconds` of continuous clear before resolving (flapping protection: a breach during recovery restarts the timer); `noDataPolicy` = `ok` (healthy) / `alert` (breach) / `keep` (no change, default); an **evaluation error changes nothing** (never resolves, never fires). | Property tests replay thousands of random sequences and assert the legal edges, the timing guarantees and that fires and resolves alternate. |
| 7 | **Incident deduplication is enforced by the database:** a unique partial index on `(orgId, projectId, ruleId, groupKey)` where `active = true`. Two workers racing, or a retry after a crash, can never create two live incidents; resolving frees the slot. | A check-then-insert in code would be racy. The test fires 10 concurrent opens and asserts one incident. |
| 8 | **Evaluation runs in the leased worker** using the Phase 2 pattern: due rules are claimed with an atomic `findOneAndUpdate` lease (oldest due first, partial index on enabled rules), evaluated with bounded concurrency, at most `maxRulesPerTick` per tick, a per-rule time budget, and the next run is **always** rescheduled (also after an error or timeout), so a slow or failing rule cannot starve the others. A rule edited during its evaluation discards that evaluation (version check). | Several workers share the load without coordination; a crashed worker's leases expire. |
| 9 | **Manual resolve while still breaching:** the group is judged afresh at the next evaluation (it passes through `pending` again and may open a new incident). Editing what a rule *measures*, disabling, or deleting it closes its live incidents (`auto_resolved`, reason recorded). | The alternative (keep the old group state) would leave a firing group with no incident, or suppress alerts for a still-broken system. |
| 10 | **Notifications: generic webhook only.** URL and signing secret are envelope-encrypted with the existing `SecretStore` (AAD-bound to org + channel), the document keeps only `scheme://host`, and no API ever returns either. Each delivery is a JSON POST signed `X-Nexus-Signature: t=<unix>,v1=<HMAC-SHA256(secret, "t.body")>` with `X-Nexus-Event` and `X-Nexus-Delivery` (receiver-side de-duplication id). | The secret is *supplied by the user* (write-only), because the receiver must know it; a server-generated secret shown once would contradict "never returned". |
| 11 | **SSRF protection reuses the platform guard** (`@nexus/security`): https required unless the platform policy allows plain http (development only); no credentials/fragments; every resolved address checked (private, loopback, link-local, metadata, mixed answers, IPv4-mapped IPv6, numeric shorthand, reserved ports) **at save time and again on every send**; the connection is pinned to the validated addresses (DNS rebinding); redirects are never followed; 5 s timeout; 16 KiB request cap; response read to 2 KiB then discarded. | Same defence as connectors (ADR-0002 #5). Tests include a real receiver that redirects, hangs and floods. |
| 12 | **Delivery queue = the `alert_deliveries` collection** (lease, attempts, `nextAttemptAt`): 5 attempts with exponential backoff (30 s, 2 min, 10 min, 30 min + jitter); 4xx (except 408/429) and blocked targets fail immediately. The same rows are the per-incident delivery log (TTL 30 days). Delivery is **at-least-once**. | One mechanism for queue and log, no extra collection. |
| 13 | **Silences** are time-bounded matchers (rules, severities, environments; AND across kinds). A matching silence turns the delivery into `suppressed` (recorded, with the silence id and a timeline event); the incident is still opened. A per-channel rate limit (default 20/min, max 60) turns excess deliveries into `rate_limited`, also recorded. Resolution notices go only to channels that were told about the opening. | Nothing disappears silently, and silence cannot hide an incident from the UI. |
| 14 | **Audit:** every configuration change and every incident action is an audit event (`alert.rule.*`, `alert.channel.*`, `alert.silence.*`, `incident.opened/acknowledged/commented/resolved/auto_resolved`), written in the same transaction as the change. Audit metadata carries field names, never values; the worker's events are `system` actors. | |
| 15 | **Limits** (schema + service layer): 100 rules, 10 channels, 50 live silences per project (atomic counters inside the creating transaction); window 1 min–24 h; interval 15 s–1 h; 20 groups per rule; 500 timeline events and 100 comments per incident; 2,000-character comments; incidents kept 90 days after resolution, deliveries 30 days. | |
| 16 | **Migration version 20** creates the collections and indexes (not the next free number, so migrations added concurrently by other work streams cannot collide; ordering in the array is what matters). | |

## Indexes (all created by migration 20 and asserted by tests)
- `alert_config`: `acfg_name_uq` unique `(orgId, projectId, kind, nameLower)` partial on `nameLower`; `acfg_scope_kind` `(orgId, projectId, kind, createdAt desc, _id desc)` for paged lists; `acfg_rule_due` `(nextEvalAt)` partial `{kind: rule, enabled: true}` for the scheduler; `acfg_silence_ttl`.
- `incidents`: **`inc_active_uq` unique `(orgId, projectId, ruleId, groupKey)` partial `{active: true}`** (the dedup invariant); `inc_scope_opened`, `inc_scope_status`, `inc_rule` for lists (explain-plan tests assert index use and no in-memory sort); `inc_ttl`.
- `alert_deliveries`: `adel_due` `(nextAttemptAt)` partial `{status: pending}`; `adel_incident`; `adel_channel_created` (per-channel rate limit); `adel_ttl`.

## Not built (honest list)
E-mail, Slack, Teams, PagerDuty/Opsgenie and any non-webhook channel · anomaly/ML detection · escalation policies · on-call schedules and rotations · incident severity changes, merging or splitting · multi-condition rules (AND/OR) · percentile aggregations · rules across several environments or projects · alert templates/variables in webhook bodies · per-user notification preferences · muting a single group · SLOs and burn-rate alerts · maintenance windows that recur · a dry-run ("preview") of a rule · receiving data from an external alert manager · exactly-once delivery.

## Known limitations that matter
- **Log counts use event time** (`ts`), so records that arrive late are counted by the evaluation after they arrive, and a log rule can under-count the most recent minute on a slow pipeline.
- **A missing metric looks like no data**, including a delta counter that simply had no increments: use `noDataPolicy = ok` for such metrics.
- **At-least-once delivery:** a worker that crashes after the receiver answered but before the row is updated resends after the lease expires; receivers should de-duplicate on `X-Nexus-Delivery`.
- **One evaluation per interval, no catch-up by default:** if the worker is down, missed evaluations are counted but, with the default `missedPolicy: skip`, not replayed; the next one looks at the current window. A per-rule `replay` policy and recurring maintenance windows were added by [ADR-0010](ADR-0010-maintenance-windows-and-replay.md).
- The window starts at the minute boundary containing `now - window` (the metric store aggregates whole minutes), so a window is up to one minute longer than configured.
- Scale: see "Measured limits" in [alerting.md](../alerting.md).
